# 把專案變成能力：六週實作路線

完成品只是起點。以下每週都要留下自己能解釋、別人能重現的產物；不要把工具生成的程式碼直接當成已掌握的能力。

| 週次 | 親手做的事 | 可展示成果與驗收 |
|---|---|---|
| 1｜理解世界 | 手動走完八個任務，解釋訂單、庫存與規則如何改變；故意重複退款與錯誤結案。 | 一張狀態轉移圖；能說明為什麼「回答完成」不等於世界正確。 |
| 2｜理解失敗 | 選三條真實模型失敗軌跡，逐步讀提示、工具結果與評分。 | 三個可重播案例；把觀察、推測與因果證據分開。 |
| 3｜改善工程 | 為記錄中斷、壞輸入或錯誤版本做故障注入；說明續跑邊界。 | 一個小修正或測試 PR，附修正前後的重現步驟。 |
| 4｜提出假設 | 在開發世界實作一個新記憶策略，例如依規則作用範圍與查詢成本決定是否查證。 | 策略不超過一頁說明；清楚列出額外資訊與成本，不偷看研究者真值。 |
| 5｜重新評估 | 先凍結提示、預算與分析方法，再建立新的測試種子／規則／任務組合。 | 新協定與實驗；保留舊結果，不反覆調整同一測試集。 |
| 6｜對外溝通 | 做三分鐘操作展示與五分鐘失敗分析，回答「為何不是多讀一次規則就好？」 | 一篇含負面結果的技術文章、一份完整重現包、一個具體未解問題。 |

## 建議研究假設

**假設 A：查證的價值取決於變動頻率與錯誤代價。** 在世界規則很少改變時，每次查證可能浪費成本；變動頻繁時，依賴被阻擋才更新可能太晚。應改變環境分布，而不只更換漂亮策略名稱。預先定義查詢成本、失誤成本與主要效用，並保留各項原始指標。

**假設 B：作用範圍可避免無關記憶一起失效。** 改變退貨規則時，出貨與改單能力應保留。但必須在更長、更平衡的任務流中驗證；目前八個任務的觀察不足。

**假設 C：狀態追蹤失敗可能比規則記憶更重要。** 模型完成修改後仍可能重複操作或錯誤結案。可以新增「已驗證效果」的記憶欄位，但要公平計入 token、工具與更新成本，也不能直接把評分器答案放進記憶。

## 需要補足的基礎

- Python 型別、例外、測試、資料序列化與 SQLite 交易。
- 狀態機、不變量、可重播事件；什麼資訊可以由重播證明。
- 條件機率、配對實驗、重抽樣信賴區間、樣本相關性與右設限。
- Transformer 推論、量化、KV cache、提示長度與延遲的關係。
- Agent 的觀察／動作界面、信任邊界與真實程式執行隔離。

先讀一條完整軌跡，再讀系統程式；先提出可以失敗的假設，再寫新策略。暫時不要把「支援更多模型、更多框架」當作研究成果本身。
